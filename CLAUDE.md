# zucchini-spawner

Rust. PowerSync sync-stream client (read-only NDJSON) + writeback. Spawns claude code on incoming user messages. `cargo check` / `cargo run`.

Installed via `install.sh`, which enrolls a Machine and runs a heartbeat. Runtime dir: `~/.zucchini-spawner/` (config, sync cursor, `key`). Dev JWT via `ZUCCHINI_DEV_JWT`.

In prod the installer registers a **per-user service** (`SERVICE_NAME=chat.zucchini.spawner`) — `systemctl --user` on Linux (loginctl linger enabled so it survives logout), launchd LaunchAgent on macOS. Read logs with `journalctl --user -u chat.zucchini.spawner -f` (Linux); on the e2e box (`beprod`) that's the source of truth for what the spawner actually did. The install/build/ship mechanics are simpler to read in `install.sh`, `build-releases.sh`, and `uninstall.sh` than to mirror here.

## Message-frame invariant

Consumes claude's `--output-format stream-json` and writes one `messages` row per JSON frame (whole frames, not token deltas — bodies are final at insert, never grow; attachments are encoded inside the body envelope so they're frozen alongside it). Combined with append-only ordering by `seq`, `(count, last.id)` is a stable identity for a chat's message array — guards like `ChatMessagesList.ApplyFingerprint` depend on this; widen them before adding edits, deletes, or out-of-envelope attachment hydration.

## Checkpoint-windowed sync reconciliation

PowerSync ops are **not** applied per-op. Within a checkpoint window the chats/projects `Put`/`Remove` and user-message `Put` arms only **stage** into a `main()`-local `SyncStaging` (`chats`/`projects: HashMap<id, StagedRow>` last-write-wins, `messages: Vec<raw row JSON>` in arrival order) — no `Mirror` mutation, no side effects, no `.await`. At `SyncEvent::CheckpointComplete` the window is applied in order **projects → chats → messages** (so `chat.project_id` and `message.chat` resolve), and **agents spawn there** (the deferred `handle_message_put`); only then does the cursor (`mirror.buckets`) advance and state.json persist. This is what kills the `PUT → REMOVE → PUT` slot-move race: the row's net final state is what gets applied, so a transient mid-turn `REMOVE` (PowerSync re-streams a chats row on any writeback, e.g. the turn's own `agent_running=false`) can no longer evict a chat between the REMOVE and re-PUT and make `send_agent_line` drop that turn's `[result]` frame. The **`machines` + `machine_users` arms stay per-op** — membership latching, `K_machine`/key-unseal, and `revoke_local_access` must take effect immediately (a `machine_users` `Remove` is a real owner-guarded removal, not a slot-move), and the first-CheckpointComplete membership latch is unchanged. Persistence is checkpoint-aligned: the cursor and state.json only advance at `CheckpointComplete`, so a mid-window crash re-streams the **whole** window from the saved cursor and rebuilds staging from scratch (staging is in-memory, never serialized, never read by the control task) — no op is dropped. The old `agent_session_id` merge-on-upsert hack in `state.rs::upsert_chat` is gone; `upsert_chat` now stores the incoming id verbatim, and preservation across a stale-NULL re-stream is an explicit **apply-phase restore** in the chats step — capture the locally-harvested session id before `upsert_chat`, and if the re-streamed row landed NULL, re-`set_agent_session_id` it (this must live in the apply phase, not a per-op upsert, because the harvest happens locally between checkpoints and a *later* window can deliver the stale NULL; fast-followup `--resume` depends on it). The replayed-message guard keys off `Mirror::handled_user_seqs` (state.json, per-chat high-water mark of handled user seqs): a message at or below the mark is a replay. `chats.last_seq` can't serve here because it also counts agent rows, which can share a window with a mid-turn user message. Without a mark (pre-upgrade state.json, fresh state, the chat's first message on this machine) it falls back to `seq < last_seq` against the window-final `last_seq`, except that for a resident (claude) chat a message followed only by user messages staged in the same window (seqs are contiguous per chat) is not a replay. A resident chat takes every message of a window in seq order; for one-shot adapters only the window's latest spawns (the earlier are superseded).

## Agent-roster seeding (`machine_users.agents`)

`machine_users.agents` is a PREFERENCE field ("what the user wants to run", owned by the clients) — the machine's install facts live in the `machines.*_installed` columns. The spawner's only touch is `seed_initial_agents_if_pending`: a **one-shot, install-time** seed of defaults (claude/cursor if installed, frozen payload bytes with deterministic `"seed-<wire_name>"` ids so concurrent client/spawner seeds converge), kept as back-compat so older App Store clients see a roster on a fresh pairing; thereafter clients own the field (newer clients seed residual NULL rows themselves). The one-shot is `Mirror::initial_agents_seed_done`, persisted in state.json and **default-FALSE** ("not done yet") — fresh installs AND pre-upgrade state.json files missing the field, which gives the cohort the old sync-gated seeder left stranded with a NULL roster exactly one healing attempt post-upgrade. Gates: seed not done yet + machine id (dev never seeds) + owner row streamed + probe results cached; drivers: every `CheckpointComplete` plus the one-shot `probe_ready_rx` retry (~5s after boot — the boot checkpoint usually applies before probes finish and an idle machine may never see another checkpoint). Zero default-seed CLIs installed still drains the flag (the install-a-CLI-later case is the clients'). Correctness does NOT depend on the flag: the backend's machine-principal `agents` write is **seed-only** (`WHERE agents IS NULL` in `put_machine_user_envelope`), so a redundant attempt — including pre-upgrade machines whose roster is already non-NULL spending their one post-upgrade attempt — drains as a 0-rows no-op. **Expect a one-time "0 rows" warn per upgraded machine in the days after a spawner release; that's the drain, not a bug.** Deploy order still matters: the backend carrying the seed-only guard must be deployed/restarted before (or together with) publishing spawner binaries, and both ship in one `backend-powersync/deploy.sh` run.

## Resident lifecycle, background tasks & the prune live-task guard

Claude is the only resident adapter: one `claude` process per chat hosts its turns and in-process background tasks/Monitors, and stays alive (warm) between turns. The other adapters spawn per turn.

**Busy/idle edges.** The reader emits the `running=false` edge only on a `result` frame with nothing else pending (**NOT** on a bare `TaskFinished` - a monitor/task completion triggers a continuation turn that ends with its own `result`, so the edge defers to the real boundary). `handle_run_state` writes `agent_running` for each edge. The resident's power assertion is held only while it is busy, so a warm idle process doesn't keep the Mac awake.

**Warm idle and eviction.** The idle edge doesn't kill the process: `SessionState::idle_since` records it, and the next message goes to stdin. `main.rs::evict_idle_residents` (policy in `warm.rs`) hard-aborts the oldest idle resident once its idle age reaches `T = 48h · 2^-((n_eff-2)^0.735)` (48h while `n_eff ≤ 2`). `n_eff` = idle footprint / (RAM/40), summed over each resident's whole process tree via a ppid walk (Playwright's browser runs in its own pgid). Footprint is macOS `ri_phys_footprint` (private + compressed) and Linux `Pss` - not RSS, which counts the shared `claude` binary once per process. Without measurements (Windows, TODO) `n_eff` is the idle count. Under memory pressure (macOS `kern.memorystatus_vm_pressure_level` ≥ warn, Linux `MemAvailable` < 10%) the oldest idle resident goes at once, one per evaluation (memory stats lag the kill). Not `kern.memorystatus_level`: it counts active pages as available, so it reads ~70% on a busy Mac and nears 10% only at jetsam. A single idle resident never expires, and busy ones and those with no idle edge yet are never evicted. Eviction runs when the idle set changes, at the next deadline, and every 60s, and writes no `interrupted` frame.

**What kills a warm process.** Besides eviction and `/kill`:
- Spawner update, crash or restart - the process dies with the spawner, so on the author's Mac every dev hot-reload kills them all. The updater waits until no agent is busy (`Supervisor::any_running`; idle residents don't count), then `shutdown_and_flush`: cancels every agent and keeps routing `response_rx` while it joins their readers (the reader goes idle on a `result` before it forwards that line's frames, and a reader blocked on the full queue only exits once it is consumed), then drains the writer. SIGTERM/SIGINT take the same path. The writer queue is in memory only: writes still unsent after `UPDATE_DRAIN_TIMEOUT` are lost.
- A prune restart or a knob respawn (see below). Both `--resume` the conversation, but drop MCP state (e.g. a Playwright browser and its page) and armed monitors, and the new process has a new pid and peer socket.
- Chat or project delete (no further writes for the deleted row), invitee revoke (no writes: the key is gone), or a flip of an invitee's sandbox setting (a running turn closes as `interrupted`).

**A new message goes to the live process's stdin** (`Supervisor::send_user_turn`) when the process is alive and was spawned with the same knobs (`SessionKnobs`: agent kind, project, worktree, sandbox, model). Claude consumes it at the next tool boundary and answers it within the running turn (one `result` covers both), or — if it lands after the last tool call — runs it as its own turn right after the running turn's `result`. Every stdin frame carries a fresh `uuid`, and `--replay-user-messages` echoes it when consumed (`AgentEvent::UserTurnConsumed`; the echo is never a message row). `SessionState.unconsumed` holds written-but-unechoed turns, registered before the write, and `running = turn_in_flight || self_turn || unconsumed || live_tasks` — so a `result` racing a queued turn can't produce the idle edge. The echo sets `turn_in_flight`. `handle_run_state` drops stale edges both ways: an idle edge emitted just before a turn was queued (`is_running` is true again), and a busy edge with no live session (e.g. queued before a `/stop`). The first turn of a spawn goes through the same queue, and a startup-timeout retry re-writes every unconsumed frame to the new process. Claude takes an injected turn as plain text and expands a slash command only as a turn of its own, so the writer holds a slash-command frame (and everything behind it) until it heads the queue with no turn in flight; the reader wakes it on each `result`.

Once the reader leaves its stdout loop the session is `closed`: it takes no more turns (`send_user_turn` and `is_running` treat it as dead), and a `Done` removes only the session that closed, never its replacement.

Otherwise (no live or open process, other knobs, or a slash command while a turn is in flight) the process is hard-aborted and a FRESH `claude --resume <agent_session_id>` spawned, re-queuing the old process's unconsumed turns ahead of the new message. The prune restart re-queues them behind its continuation prompt. Both read the unconsumed turns after the reader is joined (`abort_agent` returns them) and drop any whose uuid is already in the transcript: claude persists a consumed turn (user entry `uuid`, or a mid-turn `queued_command` attachment's `source_uuid`) and may be killed before the reader sees the echo. The `interrupted` frame goes out only if a turn was in flight or tasks were live (`is_working`), not for a turn that was merely queued. Any hard abort kills armed monitors (`--resume` can't re-arm in-process tasks). The queued/scheduled-message promoter still promotes only when the chat is idle.

**`/stop` ends the turn, `/kill` ends the process.** `/stop` on a consumed turn with nothing queued writes a stream-json `control_request` interrupt (`Supervisor::interrupt`): the process and its background tasks survive, and once claude acks it (`control_response`, which precedes the interrupted `result`) the next `result` of any origin ends the turn (an interrupted turn that merged monitor ticks is tagged `task-notification`), its frame is swallowed and `AgentResponse::Interrupted` publishes our `interrupted` frame (ignored if it comes from a session a `/kill` or respawn already replaced). A `result` before the ack is the turn's natural end: it is published as usual and the stop becomes a no-op. No `result` within 5s hard-aborts. While the interrupt is pending a new message doesn't go to stdin (the hard abort would drop it) but takes the respawn path, which re-queues it. `/stop` hard-aborts right away when turns are queued (claude would run them after an interrupt as `still_queued`, and `/stop` drops them), when only tasks are running, and for non-claude adapters (no `encode_interrupt`). `/stop` on an idle chat is a no-op. `/kill` always hard-aborts, publishes `interrupted` only if `is_working`, and writes `agent_alive=false` even with no process (the row may be stale). Both pass the membership gate first.

**Peer turns.** Another claude session on the machine can wake a warm resident with `SendMessage`. Claude echoes it on stdout as a replay user frame with `origin.kind=peer` and a uuid we never wrote; the adapter emits `PeerTurnConsumed{name, body}`, which sets `turn_in_flight` like our own echo, so busy/idle, the slash hold, stdin delivery and `/stop` all cover peer turns. The spawner publishes a `system`/`peer_message` row (older clients hide unknown system subtypes). Self-fired monitor/cron turns carry no peer origin and get no row. A `CronCreate` prompt firing on a warm idle resident isn't echoed at all (verified 2.1.265, `tmp/cron_probe.log`): only its `command_lifecycle` `started` frame, with a command uuid we never queued, announces it. That sets `SessionState::self_turn` (busy, interruptible, not evictable) until the next `result` of any origin. All Zucchini users' chats on a machine run as the same OS user, and claude's default permission mode still allows `SendMessage`, so sandboxed (invitee) spawns add `SendMessage ListAgents` to `--disallowedTools` - otherwise an invitee's session could drive the owner's bypass-mode sessions.

**`chats.agent_alive`** (migration 0048) = the chat has a resident process. Diffed once per main-loop pass (`Supervisor::alive_changes`), so prune/knob respawns don't flicker it. Clients show a dot on the chat-list avatar when `agent_alive` and the machine is online (running or idle - it marks the process, not the turn), and show Kill only when `agent_alive` (older spawners never get `/kill`). Deploy gate: `writer.rs::BACKEND_HAS_AGENT_ALIVE` stays `false` (the writes are dropped) until migration 0048 and the backend `machine_fields` allowlist are live in prod - an older backend 4xx's the batch and poisons the writer queue. Chats with `agent_running`/`agent_alive` set are persisted (`Mirror::flagged_chats`) and reset at the first checkpoint after boot, before that window's messages spawn, since PowerSync won't re-stream them. They stay flagged until the reset rows sync back, so a restart before the writer flushes resets them again. On macOS each resident's pgid + leader start time sits in `~/.zucchini-spawner/residents/`, and boot kills the groups a crashed spawner left behind (`orphans.rs`; the start time guards against pid reuse, and a group whose leader is gone is killed too - a live group's pgid can't be reused as a pid). They get SIGTERM and up to 5s before SIGKILL: claude's Bash-tool children run in groups of their own and claude reaps them only on SIGTERM. On Linux systemd kills the cgroup.

**Running a Monitor / background task is perfectly fine** — it just keeps the resident busy until it completes. The only interaction to know about is with `prune-context`: applying a prune hard-restarts the resident (abort → rewrite jsonl → respawn-with-`--resume`), and the in-process task/Monitor runtime is **not** restored by `--resume`, so a prune would kill anything in flight. Therefore `prune-context` **REFUSES** when the session has live tasks (`live_tasks` non-empty) and tells the agent to wait or pass `--force`. The check reads a shared `live_sessions` directory (`agent.rs` `LiveSessions` — the same `SessionState` Arcs the reader mutates) at RPC time so the error reaches the agent synchronously (exit 1). A forced prune (or a same-instant race) names the terminated tasks in the respawn prompt so the kill is never silent. Every other hard abort (`/kill`, `/stop`, eviction, delete, revoke, shutdown) drops the chat's parked prunes (`abort_agent`, `shutdown_all`): the torn-down session never sends their cue or a `Done`, and a stale entry would respawn the chat. An RPC still in flight can park after that clear, so the cue and the idle-edge fallback apply a prune only while the supervisor tracks an agent for the chat (`take_prunes`), and a fresh spawn drops what is parked.

## Prompt-cache discipline: nothing volatile in the system prompt

**Anything we inject per-spawn must ride the user turn, never the system prompt.** Agents respawn constantly (one-shot every turn, resident after every eviction, prune, knob change and spawner restart), and the system block sits at the head of the cacheable prefix — one changing byte there invalidates the cache for the entire conversation, which is then re-written at the 1.25x cache-write rate instead of read at 0.1x. On a long chat that costs roughly an order of magnitude of usage, growing with length.

The one volatile per-turn injection is the current-local-time line, and it has a single source: `AgentAdapter::turn_time_line`, overridden by no adapter and consumed by **both** lifecycle paths through `agent.rs`'s shared `turn_text` — `spawn_agent`'s prompt file (one-shot) and every resident stdin turn (`ResidentSession::queue_turn`). `agent_capabilities_instructions` takes no time line, so a system prompt can't carry one.

One exception rides along in `turn_text`: for an adapter that sets `expands_slash_commands` (claude only), a turn starting with a slash command (`/compact`, `/clear`, …) ships **verbatim** — no time line, preamble or first-turn suffix — because the CLI expands a slash command only when the turn starts with it, and anything prepended turns it into plain text the model answers instead of running. The gate matters: for the other adapters the same bypass would drop the once-per-chat capabilities preamble (`first_message_capabilities_preamble` is first-turn-only) and never be repaid with an expansion.

Guarded by `claude::tests::session_system_prompt_is_stable_across_respawns`. Before adding anything to a system prompt, ask whether it is identical on the next respawn — timestamps, counters, run ids and pids are not.

## Silent-startup retry

A spawn (one-shot or resident) that produces ZERO stdout+stderr within `AGENT_STARTUP_TIMEOUT` (30s) is killed and retried once with a doubled deadline — but only when some agent has already started successfully since spawner boot (`ANY_AGENT_STARTED`) and no stderr was captured (`startup_retry_allowed`, `agent.rs`). That combination is the transient-stall signature (host overload/memory pressure — SPAWNER-13); anything else fails immediately: captured stderr is surfaced as the diagnostic, and first-ever-spawn silence gets the shell-config hint. The retry is only sound BEFORE the first output frame — a started agent may have side effects, so mid-turn deaths are never retried. Deterministic hangs cost one extra 60s attempt, never a loop.

## Scope of responsibility

**Thin spawn layer — launches `claude` with our flags and that's it.** Claude's own config (`~/.claude/settings.json`, project `.claude/settings.json`, MCP allowlist, sandbox policy) is the user's responsibility, not Zucchini's. Features that touch how claude runs (e.g. the machines-sharing sandbox toggle) flip a flag on the spawn — they don't curate config or ship policy defaults; scope-of-responsibility gaps are communicated via UI disclaimers, not Zucchini-side wrappers.

**One sanctioned exception: the spawner injects a `PostToolUse` hook via `claude --settings` (in `adapters/claude.rs` `prepare_command`).** The hook command is `"$ZUCCHINI_SPAWNER_BIN" prune-reminder-hook` (a self-contained CLI subcommand in `main.rs`, no jq/script-file dependency — Rust parses the PostToolUse payload from stdin); after any tool result whose serialized `tool_response` exceeds `PRUNE_REMINDER_MIN_TOOL_RESPONSE_BYTES` (`prune.rs`) it returns `additionalContext` nudging claude to `prune-context` the output. **It also fires unconditionally for `tool_name == "Skill"`**: a Skill (and slash-command) call injects its real, often multi-100KB payload as a SEPARATE `user`/`isMeta` frame threaded by `sourceToolUseID`, NOT in `tool_response` (which is a tiny "Running skill …" ack), so the size gate alone never catches the biggest prunable chunk a turn accrues. The PostToolUse payload carries no `sourceToolUseID` and the injected body frame triggers no hook of its own, so the Skill tool call is the only handle — and the body is reclaimable via `prune-context --tool-name Skill` (the claude pruner blanks the linked `sourceToolUseID` body, not just the ack; see `adapters/claude.rs::blank_claude_entry`). This reinforces `PRUNE_CONTEXT_INSTRUCTION` at the recency frontier — claude deprioritizes the one-time `--append-system-prompt` standing order (codex/gemini comply from it; claude didn't), so the reminder is re-surfaced right after each heavy result. This is config-injection, which the rule above otherwise forbids — it's sanctioned only because it reinforces *our own* prune feature, not user policy. It stays safe because `--settings` **merges** with (never replaces) the user's `~/.claude/settings.json` / project hooks (verified empirically), so user-configured hooks survive the spawn; the hook never errors or writes partial output (always exits 0). Don't extend this into curating other claude config.

## Hot reload (author's machine)

Two launchd agents in `~/Library/LaunchAgents/`: `chat.zucchini.spawner` (the spawner) and `chat.zucchini.spawner-watcher` (runs `dev-watch.sh` on changes — builds and stages into `~/.zucchini-spawner/dev-update/`, which the running spawner's updater applies once no agent is busy, killing the warm idle residents). Watcher `WatchPaths` covers `src/` **and** `Cargo.toml`, so version bumps rebuild automatically. The machine's `spawner_version` shown in app settings is the *running* binary's `CARGO_PKG_VERSION`, written at startup — it lags until the updater swaps the binary and the spawner respawns.

## Public GitHub mirror

Mirrored to `github.com/zucchini-chat/zucchini-spawner` — the only Zucchini code that runs on user machines, so the only one we open-source. Push-only via `git subtree`; remote `spawner-public` uses SSH alias `github_zucchini_admin`. Plan + supply-chain rationale (cosign-verified releases via Sigstore, dual update channel `users.spawner_source`): `tmp/verifiable-spawner.md`.

**Sync the mirror after committing spawner changes.** From monorepo root:

```
git subtree split --prefix=zucchini-spawner --branch=spawner-export && git push spawner-public spawner-export:main
```

Subtree split reads committed history only, so a dirty working tree is fine. Required before tagging a release once cosign verification ships — the public commit at the tag is what the Sigstore signature binds to; without the sync, the release can't be reproduced or verified.
