# zucchini-spawner

Rust. PowerSync sync-stream client (read-only NDJSON) + writeback. Spawns claude code on incoming user messages. `cargo check` / `cargo run`.

Installed via `install.sh`, which enrolls a Machine and runs a heartbeat. Runtime dir: `~/.zucchini-spawner/` (config, sync cursor, `key`). Dev JWT via `ZUCCHINI_DEV_JWT`.

In prod the installer registers a **per-user service** (`SERVICE_NAME=chat.zucchini.spawner`) — `systemctl --user` on Linux (loginctl linger enabled so it survives logout), launchd LaunchAgent on macOS, a logon Scheduled Task on Windows (`install.ps1`; launcher `~/.zucchini-spawner/run.ps1`, log `spawner.log`). All three must relaunch the spawner after any exit — the self-update just swaps the binary and exits. Task Scheduler can't restart on exit (`RestartCount` covers only launch failures), so the spawner adds a once-a-minute trigger to its task at startup (`sys::ensure_supervisor_keepalive`); with `MultipleInstances=IgnoreNew` the tick is a no-op while it runs. Read logs with `journalctl --user -u chat.zucchini.spawner -f` (Linux); on the e2e box (`beprod`) that's the source of truth for what the spawner actually did. The install/build/ship mechanics are simpler to read in `install.sh`, `build-releases.sh`, and `uninstall.sh` than to mirror here. One rule that isn't obvious from them: **the shipped Linux binaries are `*-unknown-linux-musl`, statically linked** — a `-gnu` build inherits the build machine's glibc as a hard floor and dies on older servers (`version 'GLIBC_2.29' not found`), which is exactly what users run. `dev-watch.sh` keeps `-gnu` because it builds on the dev's own box for that box.

## Message-frame invariant

Consumes claude's `--output-format stream-json` and writes one `messages` row per JSON frame (whole frames, not token deltas — bodies are final at insert, never grow; attachments are encoded inside the body envelope so they're frozen alongside it). Combined with append-only ordering by `seq`, `(count, last.id)` is a stable identity for a chat's message array — guards like `ChatMessagesList.ApplyFingerprint` depend on this; widen them before adding edits, deletes, or out-of-envelope attachment hydration.

## Checkpoint-windowed sync reconciliation

PowerSync ops are **not** applied per-op. Within a checkpoint window the chats/projects `Put`/`Remove` and user-message `Put` arms only **stage** into a `main()`-local `SyncStaging` (`chats`/`projects: HashMap<id, StagedRow>` last-write-wins, `messages: Vec<raw row JSON>` in arrival order) — no `Mirror` mutation, no side effects, no `.await`. At `SyncEvent::CheckpointComplete` the window is applied in order **projects → chats → messages** (so `chat.project_id` and `message.chat` resolve), and **agents spawn there** (the deferred `handle_message_put`); only then does the cursor (`mirror.buckets`) advance and state.json persist. This is what kills the `PUT → REMOVE → PUT` slot-move race: the row's net final state is what gets applied, so a transient mid-turn `REMOVE` (PowerSync re-streams a chats row on any writeback, e.g. the turn's own `agent_running=false`) can no longer evict a chat between the REMOVE and re-PUT and make `send_agent_line` drop that turn's `[result]` frame. The **`machines` + `machine_users` arms stay per-op** — membership latching, `K_machine`/key-unseal, and `revoke_local_access` must take effect immediately (a `machine_users` `Remove` is a real owner-guarded removal, not a slot-move), and the first-CheckpointComplete membership latch is unchanged. Persistence is checkpoint-aligned: the cursor and state.json only advance at `CheckpointComplete`, so a mid-window crash re-streams the **whole** window from the saved cursor and rebuilds staging from scratch (staging is in-memory, never serialized, never read by the control task) — no op is dropped. The old `agent_session_id` merge-on-upsert hack in `state.rs::upsert_chat` is gone; `upsert_chat` now stores the incoming id verbatim, and preservation across a stale-NULL re-stream is an explicit **apply-phase restore** in the chats step — capture the locally-harvested session id before `upsert_chat`, and if the re-streamed row landed NULL, re-`set_agent_session_id` it (this must live in the apply phase, not a per-op upsert, because the harvest happens locally between checkpoints and a *later* window can deliver the stale NULL; fast-followup `--resume` depends on it). The replayed-message guard keys off `Mirror::handled_user_seqs` (state.json, per-chat high-water mark of handled user seqs): a message at or below the mark is a replay. `chats.last_seq` can't serve here because it also counts agent rows, which can share a window with a mid-turn user message. Without a mark (pre-upgrade state.json, fresh state, the chat's first message on this machine) it falls back to `seq < last_seq` against the window-final `last_seq`, except that for a resident (claude, codex) chat a message followed only by user messages staged in the same window (seqs are contiguous per chat) is not a replay. A resident chat takes every message of a window in seq order; for one-shot adapters only the window's latest spawns (the earlier are superseded).

## Agent-roster seeding (`machine_users.agents`)

`machine_users.agents` is a PREFERENCE field ("what the user wants to run", owned by the clients) — the machine's install facts live in the `machines.*_installed` columns. The spawner's only touch is `seed_initial_agents_if_pending`: a **one-shot, install-time** seed of defaults (claude/cursor if installed, frozen payload bytes with deterministic `"seed-<wire_name>"` ids so concurrent client/spawner seeds converge), kept as back-compat so older App Store clients see a roster on a fresh pairing; thereafter clients own the field (newer clients seed residual NULL rows themselves). The one-shot is `Mirror::initial_agents_seed_done`, persisted in state.json and **default-FALSE** ("not done yet") — fresh installs AND pre-upgrade state.json files missing the field, which gives the cohort the old sync-gated seeder left stranded with a NULL roster exactly one healing attempt post-upgrade. Gates: seed not done yet + machine id (dev never seeds) + owner row streamed + probe results cached; drivers: every `CheckpointComplete` plus the one-shot `probe_ready_rx` retry (~5s after boot — the boot checkpoint usually applies before probes finish and an idle machine may never see another checkpoint). Zero default-seed CLIs installed still drains the flag (the install-a-CLI-later case is the clients'). Correctness does NOT depend on the flag: the backend's machine-principal `agents` write is **seed-only** (`WHERE agents IS NULL` in `put_machine_user_envelope`), so a redundant attempt — including pre-upgrade machines whose roster is already non-NULL spending their one post-upgrade attempt — drains as a 0-rows no-op. **Expect a one-time "0 rows" warn per upgraded machine in the days after a spawner release; that's the drain, not a bug.** Deploy order still matters: the backend carrying the seed-only guard must be deployed/restarted before (or together with) publishing spawner binaries, and both ship in one `backend-powersync/deploy.sh` run.

## Resident lifecycle, background tasks & the prune live-task guard

Claude and codex are the resident adapters: one process per chat hosts its turns (claude: also its in-process background tasks/Monitors) and stays alive (warm) between turns. The other adapters spawn per turn. The machinery below is shared; the adapter supplies the wire protocol (`encode_user_turn`/`outbound_frames`, called by the stdin writer at write time on the same adapter instance the stdout reader drives). Codex specifics: **Codex resident** below.

**Busy/idle edges.** The reader emits the `running=false` edge only on a `result` frame with nothing else pending (**NOT** on a bare `TaskFinished` - a monitor/task completion triggers a continuation turn that ends with its own `result`, so the edge defers to the real boundary). `handle_run_state` writes `agent_running` for each edge. **`chats.turn_running`** (migration 0056, plaintext) is the same minus background tasks: `SessionState::in_foreground` = a turn in flight (ours, a peer's, self-fired) or a user turn queued; an internal `/rename` never counts. It is false while the chat only waits on armed tasks (`agent_running` still true) and true again for the continuation turn a task completion wakes. The backend promotes queued messages on its false edge, so every turn end must reach it. The reader captures an edge in the same lock as the event that caused it and sends it after that stdout line's frames: a turn's `result` row is queued before its false edge, and a turn queued meanwhile can't hide it. Queueing a turn on a live resident and a one-shot spawn write `true`. A false edge that finds the next turn already in the foreground is written as `false` then `true`, two patches in that order; a true edge whose turn is over, and any edge of a replaced session, is dropped. Nothing writes `false` on teardown or a one-shot's end: the backend resets it whenever `agent_running` is patched to false, and the two never share a patch. **A running watch keeps `agent_running` true like an armed task** (chat busy = its session runs OR `watch::running_in` is non-empty), in the published flag only: `Supervisor::is_running`/`any_running`, the updater's wait, `reconcile_always_on`, eviction and auto-compaction know no watches. Every `agent_running=false` goes through `main.rs::send_agent_idle` (idle edge, `Done`, interrupt-then-send, prompt retire, `/stop`, boot reset), which on a watched chat writes `turn_running=false` instead - the turn end the backend would otherwise have taken from `agent_running`. `main.rs::publish_watch_change` writes `agent_running` when a chat's watches change and no session is running: `true` with a watch, `false` (an ordinary finish) with none left. Deploy gate: `writer.rs::BACKEND_HAS_TURN_RUNNING` is `true` since migration 0056 and the backend allowlist went live in prod (2026-10-07); published spawner binaries ≤ 3.4.0 don't write the column. The resident's power assertion is held only while it is busy, so a warm idle process doesn't keep the Mac awake.

**Warm idle and eviction.** The idle edge doesn't kill the process: `SessionState::idle_since` records it, and the next message goes to stdin. `main.rs::evict_idle_residents` (policy in `warm.rs`) hard-aborts the oldest idle resident once its idle age reaches `T = 48h · 2^-((n_eff-2)^0.735)` (48h while `n_eff ≤ 2`). `n_eff` = idle footprint / (RAM/40), summed over each resident's whole process tree via a ppid walk (Playwright's browser runs in its own pgid). Footprint is macOS `ri_phys_footprint` (private + compressed), Linux `Pss` and Windows `PrivateUsage` (private commit, incl. compressed/paged-out; the Toolhelp ppid walk drops links whose parent is younger than the child, since Windows never re-parents orphans and pids get reused) - not RSS, which counts the shared `claude` binary once per process. Without measurements `n_eff` is the idle count. Under memory pressure (macOS `kern.memorystatus_vm_pressure_level` ≥ warn, Linux `MemAvailable` < 10%, Windows available physical < 10% or commit headroom < 10% of the commit limit) the oldest idle resident goes at once, one per evaluation (memory stats lag the kill). Not `kern.memorystatus_level`: it counts active pages as available, so it reads ~70% on a busy Mac and nears 10% only at jetsam. A **pinned** chat (`chats.pinned_at` non-NULL, synced to the spawner by `by_machine`'s `SELECT *` and mirrored as `ChatState::pinned`) gets `8 × T` (still capped at 48h) and is only ever picked as victim — memory pressure included — when every idle resident is pinned, so the unpinned crowd goes first. A single idle resident never expires, and busy ones and those with no idle edge yet are never evicted. Eviction runs when the idle set changes, at the next deadline, and every 60s, and writes no `interrupted` frame.

**Always-on chats** (`chats.always_on`, migration 0052, `ChatState::always_on`) count only when the machine owner owns the chat (`Mirror::is_always_on`) - a member must not pin the owner's machine. Their residents are never eviction victims, pressure included; their footprint still counts toward `n_eff`. `main.rs::reconcile_always_on` - after every checkpoint's messages and on the 60s warm tick, never before the first checkpoint - starts the resident of the next such chat that has an `agent_session_id`, a resident adapter and no agent, through the ordinary spawn with `RESTART_NOTICE` as its turn (the process was (re)started - boot, flip-on or crash - so background work may be gone; check before restarting it). The reply is an ordinary turn (rows, run state, push); the notice itself is no message row. One chat at a time and only while no agent runs or awaits a turn (armed background tasks don't count, else a restarted chat's Monitor would block the rest), so a boot doesn't run several agents at once past the clients' free-tier gate; a chat whose starts no pass saw alive `ALWAYS_ON_RETRIES` times is left alone. It runs after the window's messages, so a chat a message started is skipped. The spawner never writes the flag: the backend clears it in the same chat-row write as a `control` message insert, so it is off in the `/stop`'s own window (chats apply before messages) and the reconcile after it no longer sees the chat; `/stop` itself has no always-on logic. A client predating the `control` flag (migration 0049) leaves the flag on, so the chat restarts. state.json persists the always-on chats' `ChatState` (title excluded; the next re-stream renames the resident; the system prompt columns stay sealed) since PowerSync won't re-stream them after a restart. A window with a bucket `CLEAR` (compaction) re-streams every live row after it, so what was staged before the `CLEAR` is discarded and the chats it doesn't re-PUT are deleted (`SyncStaging::cleared`) - their `REMOVE` may have been compacted away.

**What kills a warm process.** Besides eviction and `/stop`:
- Spawner update, crash or restart - the process dies with the spawner, so on the author's Mac every dev hot-reload kills them all. The updater waits until no agent is busy (`Supervisor::any_running`; idle residents don't count), then `shutdown_and_flush`: cancels every agent and keeps routing `response_rx` while it joins their readers (the reader goes idle on a `result` before it forwards that line's frames, and a reader blocked on the full queue only exits once it is consumed), then drains the writer. SIGTERM/SIGINT take the same path. The writer queue is in memory only: writes still unsent after `UPDATE_DRAIN_TIMEOUT` are lost.
- A prune restart or a knob respawn (see below). Both `--resume` the conversation, but drop MCP state (e.g. a Playwright browser and its page) and armed monitors, and the new process has a new pid and peer socket.
- Chat or project delete (no further writes for the deleted row), invitee revoke (no writes: the key is gone), or a flip of an invitee's sandbox setting (a running turn closes as `interrupted`).

**A new message goes to the live process's stdin** (`Supervisor::send_user_turn`) when the process is alive and was spawned with the same knobs (`SessionKnobs`: agent kind, project, worktree, sandbox, model, user system prompt). Claude consumes it at the next tool boundary and answers it within the running turn (one `result` covers both), or — if it lands after the last tool call — runs it as its own turn right after the running turn's `result`. Every stdin frame carries a fresh `uuid`, and `--replay-user-messages` echoes it when consumed (`AgentEvent::UserTurnConsumed`; the echo is never a message row). `SessionState.unconsumed` holds written-but-unechoed turns, registered before the write, and `running = turn_in_flight || self_turn || unconsumed || live_tasks` — so a `result` racing a queued turn can't produce the idle edge. The echo sets `turn_in_flight`. `handle_run_state` drops stale edges both ways: an idle edge emitted just before a turn was queued (`is_running` is true again), and a busy edge with no live session (e.g. queued before a `/stop`). The first turn of a spawn goes through the same queue, and a startup-timeout retry re-writes every unconsumed frame to the new process. Claude takes an injected turn as plain text and expands a slash command only as a turn of its own, so the writer holds a slash-command frame (and everything behind it) until it heads the queue with no turn in flight; the reader wakes it on each `result`.

Once the reader leaves its stdout loop the session is `closed`: it takes no more turns (`send_user_turn` and `is_running` treat it as dead), and a `Done` removes only the session that closed, never its replacement.

Otherwise (no live or open process, other knobs, or a live-typed slash command while a turn other than a `/compact` is in flight - a running compaction is waited for; a slash command the backend promoted from the schedule, `messages.auto_sent`, never cuts a turn: `Supervisor::send_scheduled_turn` queues it and the writer holds it until the turn's `result`) the process is hard-aborted and a FRESH `claude --resume <agent_session_id>` spawned, re-queuing the old process's unconsumed turns ahead of the new message. The prune restart re-queues them behind its continuation prompt. Both read the unconsumed turns after the reader is joined (`abort_agent` returns them) and drop any whose uuid is already in the transcript: claude persists a consumed turn (user entry `uuid`, or a mid-turn `queued_command` attachment's `source_uuid`) and may be killed before the reader sees the echo. The `interrupted` frame goes out only if a turn was in flight or tasks were live (`is_working`), not for a turn that was merely queued. Any hard abort kills armed monitors (`--resume` can't re-arm in-process tasks). The backend promotes a timed scheduled message when it is due, whatever the agent is doing, and a queued one when the turn ends (`turn_running` false).

**`/stop` ends the turn and the process.** `/stop` (and `/kill`, kept as its alias for older clients) hard-aborts the chat's agent (`main.rs::stop_agent`): the process group is killed, background tasks and queued turns included, while the transcript stays, so the next message `--resume`s it in a fresh process. It always removes the chat's watches too (**Watches** below). It publishes `interrupted` only if `is_working`, `agent_running=false` (`stopped_by_user`, no push) if it was running or had a watch, and `agent_alive=false` even with no process (the row may be stale); on an idle chat it still kills the process. It passes the membership gate first.

**Peer turns.** Another claude session on the machine can wake a warm resident with `SendMessage`. Claude echoes it on stdout as a replay user frame with `origin.kind=peer` and a uuid we never wrote; the adapter emits `PeerTurnConsumed{name, body}`, which sets `turn_in_flight` like our own echo, so busy/idle, the slash hold and stdin delivery all cover peer turns. The spawner publishes a `system`/`peer_message` row (older clients hide unknown system subtypes). Self-fired monitor/cron turns carry no peer origin and get no row. A `CronCreate` prompt firing on a warm idle resident isn't echoed at all (verified 2.1.265, `tmp/cron_probe.log`): only its `command_lifecycle` `started` frame, with a command uuid we never queued, announces it. That sets `SessionState::self_turn` (busy, not evictable) until the next `result` of any origin. All Zucchini users' chats on a machine run as the same OS user, and claude's default permission mode still allows `SendMessage`, so sandboxed (invitee) spawns add `SendMessage ListAgents` to `--disallowedTools` - otherwise an invitee's session could drive the owner's bypass-mode sessions.

**Session name = chat title.** Every claude spawn passes `--name <title>` (`session_name::from_title`: whitespace/ZWJ collapsed, `[]`→`()` since brackets are `SendMessage`'s ref syntax, leading `-` stripped so it can't parse as a flag, cut to 40 chars on a word boundary; blank ⇒ no flag and claude derives `<dir>-<hex>`). That name is what another agent on the machine sees in `ListAgents` and addresses with `SendMessage`, so a chat renamed "cover letters writer" is reachable by that name. `chats.title` is decrypted in `upsert_chat` (owner's key; `None` until it unseals, healed by the next re-stream — a chats row re-streams on every writeback) and kept plaintext in `ChatState` only, never in state.json. Claude resolves a collision with another live session itself (`session_name_collision`) by taking a suffixed variant; we don't dedup. **Renaming a live claude resident (`names_session`; codex has no peer names) sends it an INTERNAL `/rename <name>` turn** (`Supervisor::rename_resident`). Editing its entry in claude's session registry (`~/.claude/sessions/<pid>.json`) instead was wrong: the file alone doesn't touch the process's in-memory name, so the renamed session kept announcing its OLD one in the `from-name=` of every peer message it sent, misattributing fan-out replies. `/rename` fixes both halves — verified on 2.1.265 (`tmp/rename_turn_probe.py`): claude handles it locally in <100ms, no model call and no tokens. The turn is the SPAWNER's, not the user's (`QueuedTurn.internal`), so it is invisible: `SessionState::running()` skips it both queued and in flight, which means no `agent_running` edge, hence no "agent finished" push, no scheduled-message promotion and no move of the eviction clock (`idle_since`). **The rename writes NOTHING — not one message row** (a row would bump the chat: unread, preview, notification). Everything it emits is dropped (`internal_turn_swallows`) between the `command_lifecycle` started (`AgentEvent::TurnStarted`, which precedes the echo — the assistant text comes BEFORE the `user` echo) and the next `result`, which just closes the window: its frames, its result frame, and its usage (a local command must not move the context gauge). Suppression is latched per stdout LINE (`InternalLine`), because one line yields several events: a `result` line yields `Result` — which closes the window — and then the result frame itself, which still belongs to the rename. Renames queued back to back each stay tracked (`SessionState.internal` is a list of uuids, `internal_running` the one in flight), so the second can't erase the first and leave its echo to be counted as the user's turn (busy edge, push, promotion, eviction clock). Fail-open: a foreign `UserTurnConsumed` or a peer turn inside that window closes it, so real content can never be swallowed. Being a slash command it's an `own_turn`, so the writer holds it until it heads the queue with no turn in flight and `turn_text` ships it verbatim — the existing machinery, no special case; a respawn drops it rather than re-queuing it (`abort_agent` filters it out; the fresh spawn passes `--name` from the current title anyway). Dedup is mandatory — a chats row re-streams on EVERY writeback, so `rename_resident` queues only when the title differs from the name this process was last ASKED for (`ResidentSession.asked_name`, seeded with the spawn-time `--name`, so a chat that came up under its current title queues nothing). A title that sanitizes to nothing arrives as `None` and leaves the resident under its current name. Known gaps: a rename waits behind a long running turn; two live residents renamed to the same title keep duplicate handles (claude only de-dups at spawn; `SendMessage` still disambiguates with `[ref]`); and a `/rename` that fails leaves the name stale until the next respawn, which re-applies `--name`. `claude --name` needs **claude ≥ 2.1.76** (2026-03-14) — an older CLI rejects the flag (exit 1, empty stdout, `error: unknown option '--name'` on stderr), which the never-started branch of `stderr_failure_message` surfaces as a message row in the chat. That's why we don't probe the version.

**`chats.agent_alive`** (migration 0048) = the chat has a resident process. Diffed once per main-loop pass (`Supervisor::alive_changes`), so prune/knob respawns don't flicker it. Clients show a dot on the chat's avatar when `agent_alive` and the machine is online (running or idle - it marks the process, not the turn), and older clients show Kill (which sends `/kill`, now an alias of `/stop`) only when `agent_alive`. Deploy gate: `writer.rs::BACKEND_HAS_AGENT_ALIVE` stays `false` (the writes are dropped) until migration 0048 and the backend `machine_fields` allowlist are live in prod - an older backend 4xx's the batch and poisons the writer queue. Chats with `agent_running`/`agent_alive` set are persisted (`Mirror::flagged_chats`) and reset at the first checkpoint after boot, before that window's messages spawn, since PowerSync won't re-stream them. They stay flagged until the reset rows sync back, so a restart before the writer flushes resets them again. On macOS each resident's pgid + leader start time sits in `~/.zucchini-spawner/residents/`, and boot kills the groups a crashed spawner left behind (`orphans.rs`; the start time guards against pid reuse, and a group whose leader is gone is killed too - a live group's pgid can't be reused as a pid). They get SIGTERM and up to 5s before SIGKILL: claude's Bash-tool children run in groups of their own and claude reaps them only on SIGTERM. On Linux systemd kills the cgroup.

**`chats.live_tasks`** (migration 0050) = the chat's watches plus what the resident has armed RIGHT NOW, so the clients' "Background work" sheet (a tap on the Thinking/Waiting pill) can list it. Encrypted like `messages.body` (`encrypt_field_b64` under the chat owner's key); plaintext shape `{"t":[{"i":<task_id>,"d":<description, ≤200 chars>,"k":"watch"|"bash"|"agent"|<raw task_type>,"a":<subagent_type, omitted when absent>,"s0":<start epoch ms>}],"q":<queued USER turns>}` — `t` omitted when empty, `q` when 0, and the whole column NULL when the chat has no watch, nothing armed and nothing queued. `t` lists the chat's watches first (`i` = watch id, `s0` = its creation; oldest first), then the session's tasks, at most 20 entries together, so of the tasks the OLDEST stay. The session's own blob (`live_tasks_payload`) knows no watches: `agent::live_tasks_with_watches` adds them in the one writer, `main.rs::write_live_tasks`, behind the dedup and the stale-snapshot check below, which compare session blobs only. The prompts themselves never ride along (they're already user bubbles above the pill), and `q` uses the same `user_queued()` predicate `running()` does, so an internal `/rename` never counts. `SessionState::live_tasks` is a `Vec<LiveTask>` in ARM order (the client renders it in that order); claude's `task_started` frame carries `description`/`task_type`/`subagent_type` and the spawner stamps `started_at` on arrival (the frame has no start time). The READER publishes it (`AgentResponse::LiveTasks`) — a main-loop diff à la `alive_changes` would be wrong here because a task edge publishes no frame, so nothing would wake the loop until the next 60s eviction pass. It is NOT the only publisher: queueing a turn on a live resident changes `q` and produces no adapter output until the echo, so `handle_message_put` publishes at the enqueue edge too (`Supervisor::live_tasks_change`). Both go through ONE dedup on the serialized payload — `SessionState::published_live_tasks` (`LiveTasksDedup`, same shape as `LastTokensDedup`), read via `observe_live_tasks`; a per-publisher dedup would let each side re-write what the other already wrote, or swallow a change. A late edge from a session a teardown already replaced is dropped (`is_current_session`); buffered reader snapshots must also match the current `live_tasks_payload` before publication, because a newer enqueue write can overtake them and the shared dedup cannot repair a stale overwrite. Deploy gate: `writer.rs::BACKEND_HAS_LIVE_TASKS` is `true` since migration 0050 and the backend `machine_fields` allowlist went live in prod (2026-09-12); published spawner binaries ≤ 3.2.3 still carry `false`. **Armed tasks die with the process, so EVERY teardown clears them** (`main.rs::clear_live_tasks`: NULL, or the watches alone for a chat that has some - the daemon runs those, with or without an agent process) — including one that tears down a WARM IDLE resident (a sandbox flip; the reader's own clear can still be in the response queue, where `is_current_session` then drops it as a replaced session's): `Done`, `/stop`, eviction, prune restart, knob respawn, sandbox flip, and spawner shutdown/update — the last one explicitly per torn-down chat at the END of `shutdown_agents`, because `cancel_all` drains the supervisor first, so the `Done`s routed during the drain no longer recognize the chat's agent (and a reader that misses `AGENT_EXIT_TIMEOUT` sends no `Done` at all). The backstop is the boot reset: `Mirror::flagged_chats` flags a chat on `agent_running` OR `agent_alive` OR a non-NULL `live_tasks`, so a blob left by any missed clear is reset at the first checkpoint of the next start (`Mirror::first_checkpoint`) — flagging on the run flags alone would miss it, since a row can carry tasks with both flags already false. A watched chat is therefore reset at every boot; the reset writes its watches back and leaves `agent_running` to them. A deleted chat and a revoked member get no writes at all, as everywhere else. `v1` ignores claude's `task_progress` frames (they keep falling through the `system` skip); adding them later is a pure extension of the same blob.

**Codex resident** (`adapters/codex.rs`; protocol spike with raw captures: `tmp/codex-appserver-spike.md`, codex-cli 0.154). One `codex app-server` per chat, JSON-RPC over stdio. The writer sends `initialize`, then (on its answer) `initialized` + `thread/resume <agent_session_id>` or `thread/start` with cwd/sandbox/model/`approvalPolicy: never`; turns are held until the thread id comes back (it is the session id; threads `codex exec` created resume fine, and back). Codex writes no rollout before a thread's first turn, so a resume answered `no rollout found` falls back to `thread/start` (the new id is harvested). The startup watchdog runs until the thread opens or fails (`startup_complete`), not until the first stdout line - codex chatters from launch. Every `turn/started` is a `TurnStarted`, so a turn nobody sent (a goal continuation) is busy like claude's self-fired turns. Every user turn is a `turn/start` with `clientUserMessageId` = our uuid: on a busy thread it joins the running turn, and the `userMessage` item's `clientId` echo is `UserTurnConsumed` (the id is persisted in the rollout, so `turns_to_requeue` works). JSON-RPC ids are strings naming what they answer (`turn:<uuid>`, `compact:<uuid>`); a refused turn is consumed and answered with an error result, and an accepted turn whose echo never came is consumed when its turn (id from the `turn/start` answer) completes - else the chat would stay busy forever, never evicted and blocking self-update. A thread that fails to open fails the next turn with the reason, then the writer closes stdin (`session_over`) so the next message respawns. `/compact [instructions]` = `thread/compact/start` (instructions are dropped - the request takes none): a command turn (`is_command_turn`) that ships verbatim (no time line) and waits in the queue until the chat is idle, because compacting a busy thread interrupts its turn; nothing behind it is written until it is consumed and its result arrives (`command_runs_alone` + `SessionState::command_in_flight`; claude's `/compact` is held the same way, its other commands aren't); the writer re-checks after every stdout line (`writer_follows_every_line`; claude only after a `result`); it emits `CompactBoundary` from the last `thread/tokenUsage/updated` `last.totalTokens` (`last.inputTokens` is 0 after a compaction). Other codex TUI slash commands reach the model as text. The gauge is `thread/tokenUsage/updated` `last.totalTokens`. Gotchas: **teardown closes stdin** (`exits_on_stdin_eof`: writer dropped, stdout drained for up to `STDIN_EOF_GRACE`, then the usual SIGTERM) - SIGTERM leaves the shell commands codex runs in process groups of their own orphaned, and the boot orphan reaper can't see them either; a **prune needs the restart** - a live `thread/resume` keeps the in-memory history, only stdin EOF → rewrite → new process → `thread/resume` sees the rewritten rollout; codex's MCP servers are per thread and stay resident while idle (~0.5 GB tree), which the eviction footprint walk counts. A model/sandbox/worktree change still respawns (knobs), though `turn/start` could override model and sandbox per turn. Opt-in e2e smoke against the real CLI: `cargo test codex_resident_smoke -- --ignored --nocapture` (`agent.rs`).

**Auto-compaction** (`chats.auto_compact_tokens`, migration 0054, `ChatState::auto_compact_tokens`; claude and codex only). The resident reader sends `AgentResponse::TurnEnded` on every non-internal `result` that leaves no turn in flight (armed background tasks allowed), ahead of that result's idle edge; the main loop hands it to `Supervisor::after_turn` → `SessionState::after_turn`. If the last reported context (`SessionState::context_tokens`, from `ContextTokens`/`CompactBoundary` - the number the client gauge shows) is ≥ the threshold, no user turn is queued and no subagent (`local_agent`) task is armed, it queues `/compact <AUTO_COMPACT_INSTRUCTIONS>` as an ordinary turn on the live resident. A checkpoint that changes a chat's threshold runs the same check at once, after that window's messages (`Supervisor::after_threshold_set`, skipped while a compaction is under way), so a threshold set below an idle resident's context compacts it immediately; that compaction starts from idle, so its end is an ordinary idle edge (finished push). Queued before the idle edge, it keeps the chat busy (main drops that edge as stale), so no finished push or scheduled-message promotion fires between the turn and the compaction. `/compact` runs alone (`command_runs_alone`), so messages arriving meanwhile wait for its `result`. On an always-on chat the compaction's end queues `AUTO_COMPACT_NOTICE` (re-read standing instructions, check armed tasks) the way `RESTART_NOTICE` starts a resident: a normal turn whose prompt is no message row. The end of the compaction or the notice never compacts again (`AutoCompact` state), so a context that stays above the threshold re-compacts after the next other turn, not in a loop; the thrash guard is in `BACKLOG.md`. The state lives in the session, so a respawn drops it.

**User system prompt** (`chats.system_prompt_files` + `chats.system_prompt`, migration 0055; claude only - `AgentAdapter::takes_user_system_prompt`, other kinds ignore the columns; a sandboxed member's chat gets none either). Both are K_machine-sealed like the title: a comma-separated file list and free text, as the user typed them. The backend caps each ciphertext at 20,000 chars, because the chats row re-streams on every writeback; clients cap the text at 8 KB and point longer instructions to a file. `ChatState` keeps them sealed (so state.json, which persists always-on chats, holds no plaintext; `Mirror::unseal_system_prompts` decrypts after load) and decrypted as `user_system_prompt` (`user_prompt::UserSystemPrompt`). Every spawn and the retire check read it through `Mirror::user_system_prompt`, which is empty for a sandboxed member's chat (a member whose `machine_users` row hasn't synced counts as sandboxed): the spawner reads the files with its own access, outside claude's permission gating, so for such a chat the columns change nothing - no knob difference, no retire, no decrypt error. Clients hide the UI there; this is the enforcement. A sandbox flip tears the member's residents down (`abort_member_agents`), so the next spawn picks the prompt up or drops it. A set column that fails to decrypt marks it `undecryptable` (with a warn), which fails the spawn: a chat never runs without the instructions its user set. It is a spawn knob, so a message that finds the resident running with another value respawns it (`--resume`), cutting a running turn like a model change does. At spawn (`default_resident_spawn_fn`; the one-shot path takes no prompt) `UserSystemPrompt::render` reads the files in Rust and appends to `--append-system-prompt`, after our instructions: a header line, each file as `<file path="<as typed>">…</file>`, then the text. Paths: split on `,`, trimmed, empties skipped; relative ones resolve against the project path (not the worktree), `~/` is the home dir, absolute paths and `..` are allowed. Each path is canonicalized once and that canonical path is what gets opened. Only a regular file is read (checked on the open handle, opened non-blocking so a FIFO can't hang the spawn), and at most the cap plus one byte. The rendered block is capped at 64 KB on unix, counted as it lands in the `bash -lic` argument (a `'` costs 4 bytes; Linux caps one argument at 128 KB), and at 20 KB on Windows, counted with argv escaping (a `"` or `\` costs 2), which leaves room for our own ~4 KB of flags under CreateProcess's 32,767 chars (`claude::tests::a_full_user_prompt_fits_the_windows_command_line`). A missing, unreadable, non-regular, non-UTF-8 or oversized file, a block over the cap, or an undecryptable column fails the spawn like any other spawn failure (`fail_agent`: an `Error: …` row naming the file and reason, then `interrupted`). The text lands in the process argv (visible to `ps`), like the title.

A chats row whose prompt differs from what the live resident was spawned with tears it down (`main.rs::retire_stale_prompt`) once no turn would be cut: no turn in flight or queued, no subagent armed. The new prompt is rendered first, and one that doesn't render retires nothing (warn): the resident keeps working and the next message's respawn reports the error. That is checked after the checkpoint's messages, on the idle edge, on `TurnEnded` for an always-on chat left with background tasks armed (it sends no idle edge), and for always-on chats on the 60s warm tick (`tend_always_on`). A resident with background shells/monitors armed goes only if the chat is always-on and no agent is in the foreground, i.e. `reconcile_always_on` can restart it at once with `RESTART_NOTICE`, which has the agent re-arm them (`agent_running` cleared as `stopped_by_user`, no `interrupted` frame); otherwise it waits, the warm tick retrying. A resident with nothing armed goes at once, and one that isn't always-on respawns on its next message. A row that changes the prompt resets the chat's `always_on_starts`, so prompt edits never use up `ALWAYS_ON_RETRIES` and fixing a prompt that failed to render restarts the chat. Editing a file's content triggers nothing: it applies at the next respawn.

**Running a Monitor / background task is perfectly fine** — it just keeps the resident busy until it completes. The only interaction to know about is with `prune-context`: applying a prune hard-restarts the resident (abort → rewrite jsonl → respawn-with-`--resume`), and the in-process task/Monitor runtime is **not** restored by `--resume`, so a prune would kill anything in flight. Therefore `prune-context` **REFUSES** when the session has live tasks (`live_tasks` non-empty) or, for codex, shell commands still running (`SessionState::live_commands`, from `commandExecution` started/completed, the prune call itself exempt; they never make the chat busy - a dev server would keep it busy forever), and tells the agent to wait or pass `--force`. The check reads a shared `live_sessions` directory (`agent.rs` `LiveSessions` — the same `SessionState` Arcs the reader mutates) at RPC time so the error reaches the agent synchronously (exit 1). A forced prune (or a same-instant race) names the terminated tasks in the respawn prompt so the kill is never silent. Every other hard abort (`/stop`, eviction, delete, revoke, shutdown) drops the chat's parked prunes (`abort_agent`, `shutdown_all`): the torn-down session never sends their cue or a `Done`, and a stale entry would respawn the chat. A cue arriving while the chat is idle is dropped rather than applied. An RPC still in flight can park after that clear, so the cue and the idle-edge fallback apply a prune only while the supervisor tracks an agent for the chat (`take_prunes`), and a fresh spawn drops what is parked.

## Watches (`watch.rs`)

`zucchini-spawner watch create --cmd … --ttl … --description …` (agent-run, all three required, chat from `ZUCCHINI_CHAT_ID`, cwd = the caller's) has the **daemon** run a shell command (login shell, own process group) until it exits or its TTL passes. Stdout lines within 200 ms become one message into the owning chat; any exit of the command (code 0, another code, a signal) ends the watch - it is never restarted after an exit, the agent creates it again. The description names the watch: it is unique among the chat's running watches (`create` refuses a second one). `watch list` and `watch delete --description` reach only the calling chat's watches; the id (the storage dir, `live_tasks.i`) is never shown to an agent.

- **Storage** `~/.zucchini-spawner/watches/<id>/`: `watch.json` (definition), `state/` (the command's cursor dir, `$ZUCCHINI_WATCH_STATE_DIR`), `outbox/` (one file per undelivered message), `stderr.log` (current run, truncated at each launch); next to them `stopped/<chat_id>`, the `/stop` notes (below). A watch on disk is loaded at boot (listed, its chat's row kept) but runs only from the first checkpoint on (`watch::admit_restored`), once its chat's access is known again. Child groups are recorded in `residents/` like resident agents, so the boot orphan sweep kills what a crashed spawner left.
- **Delivery** is local, like a peer turn: the watch hands everything queued in its outbox, as one message, to the main loop (`main.rs::deliver_watch_message`), which writes a `system`/`peer_message` row (`name` = `watch "<description>"`, so every client shows "Message from watch …" as a system frame, never a user bubble) and starts the turn through `start_turn`, the path a user message takes: a live resident gets it on stdin and answers within the running turn, otherwise a fresh process is spawned. The prompt is `[zucchini watch "<description>"]` plus the lines; it is no message row. Refused, and offered again every 15 s from the outbox: before the first checkpoint, a chat or project not in the mirror, a one-shot adapter's agent still running (the turn would cut it). One loop per watch delivers for its whole life and waits for each answer, so the command's exit can't repeat a message; only a cancel (shutdown, delete) drops a delivery in flight, which the next start may repeat. A stdout line is kept up to 8 KB and the rest of it discarded (`[output truncated]`); lines that together exceed 8 KB go out as several messages, each counted by the flood guard. A message taken while the backend is unreachable is not held back: its row waits in the writer's in-memory queue and the agent's turn fails on its own API call, with the text left in its transcript.
- **A watched chat's row is persisted** in state.json like an always-on chat's (`state.rs::serialize_kept_chats`), since the spawn needs it and PowerSync won't re-stream it after a restart. `control.rs::create_watch` saves state.json itself, under the mirror's write lock (the access check, the registration and the save are one step against a revoke and against the main loop's saves), so a crash right after a create can't leave a watch whose chat the next boot doesn't know.
- **Ends** with a notice to the chat that says how: the command's exit (`exited with code N` / `was killed by a signal` / `could not be started (…)`, e.g. a cwd that is gone), TTL (no default, `--ttl forever` for none; checked on the wall clock so machine sleep counts) and flood (more than 120 messages in 10 min). The directory stays until the outbox is delivered and then goes, `stderr.log` included, so the notice of a failed run carries the last 1 KB of its stderr (`stderr.log` is emptied whenever it passes 1 MB). Removed silently by a `/stop` (below), when the chat is deleted (`delete_chat`) or its member is revoked or re-sandboxed (`abort_member_agents`), and at the first checkpoint after boot when its chat is not in the mirror or lost its access (below). However a run ends, its process group gets SIGTERM and, after 5 s, SIGKILL for whatever is left (`sys::stop_process_group`), also when the shell itself exited. A chat deleted while the spawner was down, whose `REMOVE` was compacted away, leaves its watch running until the TTL.
- **Listed in `chats.live_tasks`** (see that paragraph) as `k: "watch"` entries from creation until the command is over or the watch is removed - a watch parked at boot and one stopped by a spawner shutdown included, one only draining its outbox not. `watch.rs` sends the chat id (`watch::Changed`) when a watch is created, admitted at boot or gone for good, and the main loop rewrites the column from the chat's current session, if any, plus its watches (`main.rs::publish_watch_change`; nothing before the first checkpoint, for a chat not in the mirror, or for a user whose key is gone).
- **A chat with a running watch is `agent_running = true`**, like one with an armed background task (**Busy/idle edges** above); `turn_running` and `agent_alive` are untouched. `publish_watch_change` writes the flag with the list: `true` for a watch on a chat with no running agent, `false` once the last one is gone and no agent runs. A watch that ends with a notice is reported gone only when its chat took the notice, so the turn the notice starts carries the flag to its own idle edge and the chat finishes once; while the notice can't be delivered the chat stays `agent_running` with the watch already off the list. Boot: `admit_restored` runs before the flagged-chat reset, so the reset of a chat with an admitted watch writes `turn_running=false` and its watches, and the admission's change then writes `agent_running=true`; a refused watch's chat is reset to false/NULL. While the spawner is down (shutdown, update) a watched chat's row keeps `agent_running=true` and its watches - the watches stopped by the shutdown still count for the teardown writes - and the next boot's reset re-derives both.
- **`/stop`** (`main.rs::stop_agent`) always removes the chat's watches, silently - no notice, no turn, no message row, undelivered messages dropped - whether or not an agent was working, and clears `agent_running` as `stopped_by_user`. What it removed is appended to `watches/stopped/<chat_id>` (description and command, one line each, so it survives a spawner restart), and `start_turn` prepends it once to the chat's next turn that is no command turn (those ship verbatim): `[zucchini] The user pressed Stop, which also removed this chat's watches: "<description>" (<cmd>), … They are not running any more.` That covers a user message, a promoted scheduled message and a watch's message, on a fresh spawn and on a live resident's stdin; an always-on `RESTART_NOTICE` spawn doesn't take it. The note is part of the turn's prompt, so a respawn re-queues it with the turn.
- **Access** (`Mirror::can_watch`, checked at create/list/delete, at every delivery and at the first checkpoint): the chat's user is the owner or an unsandboxed member and their key is on the machine - the command runs as the spawner's OS user outside claude's sandbox, and a soft-revoked member keeps their unsandboxed `machine_users` row and loses only the key. At most 50 watches per machine.
- Spawner shutdown/update and uninstall stop the commands (SIGTERM, 5 s, SIGKILL) and the next start relaunches them with their `state/` intact (a stop by the spawner is not an exit of the command), so on the author's Mac every hot reload restarts every watch. An update stops them only once the new binary is in place, so a failed download leaves them running. After the stop `watch create` is refused.
- Not built: webhook watches (backend stores each POST and relays it over the sync stream). The outbox, TTL, notices and lifecycle don't depend on the source being a command.

## Prompt-cache discipline: nothing volatile in the system prompt

**Anything we inject per-spawn must ride the user turn, never the system prompt.** Agents respawn constantly (one-shot every turn, resident after every eviction, prune, knob change and spawner restart), and the system block sits at the head of the cacheable prefix — one changing byte there invalidates the cache for the entire conversation, which is then re-written at the 1.25x cache-write rate instead of read at 0.1x. On a long chat that costs roughly an order of magnitude of usage, growing with length.

The one volatile per-turn injection is the current-local-time line, and it has a single source: `AgentAdapter::turn_time_line`, overridden by no adapter and consumed by **both** lifecycle paths through `agent.rs`'s shared `turn_text` — `spawn_agent`'s prompt file (one-shot) and every resident stdin turn (`ResidentSession::queue_turn`). `agent_capabilities_instructions` takes no time line, so a system prompt can't carry one.

One exception rides along in `turn_text`: a command turn (`AgentAdapter::is_command_turn` — any leading slash command for claude, `/compact` for codex) ships **verbatim** — no time line, preamble or first-turn suffix — because the CLI recognizes it only when the turn starts with it, and anything prepended turns it into plain text the model answers instead of running. Except on a first turn with a preamble (codex): that preamble is never sent again, so a chat's first `/compact` goes as text. The gate matters: for the other adapters the same bypass would drop the once-per-chat capabilities preamble (`first_message_capabilities_preamble` / `session_first_turn_preamble` are first-turn-only) and never be repaid with an expansion.

The user system prompt (above) is appended last and renders the same bytes for unchanged fields and files; editing a listed file changes the system block at the next respawn, which is the user's call.

Guarded by `claude::tests::session_system_prompt_is_stable_across_respawns`. Before adding anything to a system prompt, ask whether it is identical on the next respawn — timestamps, counters, run ids and pids are not.

## Silent-startup retry

A spawn (one-shot or resident) that produces ZERO stdout+stderr within `AGENT_STARTUP_TIMEOUT` (30s) is killed and retried once with a doubled deadline — but only when some agent has already started successfully since spawner boot (`ANY_AGENT_STARTED`) and no stderr was captured (`startup_retry_allowed`, `agent.rs`). That combination is the transient-stall signature (host overload/memory pressure — SPAWNER-13); anything else fails immediately: captured stderr is surfaced as the diagnostic, and first-ever-spawn silence gets the shell-config hint. The retry is only sound BEFORE the first output frame — a started agent may have side effects, so mid-turn deaths are never retried. Deterministic hangs cost one extra 60s attempt, never a loop.

## Windows-native launch

On Windows an adapter that offers `prepare_native` (`NativeSpawn`) is spawned shell-free through `shell::native_command`; the others go through Git Bash `-lic` like on unix. Claude runs `claude.exe` directly. Cursor's Windows installer ships only `cursor-agent.cmd`/`.ps1` shims, which bash can't resolve, so cursor runs as `pwsh -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <cursor-agent.ps1> <flags>` (script from PATH, else `%LOCALAPPDATA%\cursor-agent`), which keeps Cursor's own version-picking launcher and passes UTF-8 stdin/stdout, quoted args and the exit code through. The flag list (`cursor_flag_args`) and stdin preamble (`stdin_preamble`) are shared with the bash path; natively the preamble is prepended into the prompt file, which feeds stdin. The probe matches: installed = `pwsh` (PowerShell 7) and the script resolve, authenticated = `status --format json` through the same launcher. A silent-startup retry reopens the prompt file, since the killed child shared the stdin handle's file position. Opt-in smoke against the real CLI: `cargo test cursor_oneshot_smoke -- --ignored --nocapture` (`agent.rs`).

## Scope of responsibility

**Thin spawn layer — launches `claude` with our flags and that's it.** Claude's own config (`~/.claude/settings.json`, project `.claude/settings.json`, MCP allowlist, sandbox policy) is the user's responsibility, not Zucchini's. Features that touch how claude runs (e.g. the machines-sharing sandbox toggle) flip a flag on the spawn — they don't curate config or ship policy defaults; scope-of-responsibility gaps are communicated via UI disclaimers, not Zucchini-side wrappers. Where `--print` ignores a user's own claude setting, the spawner mirrors it into a flag instead: `claudeInChromeDefaultEnabled` in `~/.claude.json` → `--chrome` (read per spawn, owner spawns only — the browser carries the owner's logins; `adapters/claude.rs::claude_in_chrome_enabled`).

**One sanctioned exception: the spawner injects a `PostToolUse` hook via `claude --settings` (in `adapters/claude.rs` `prepare_command`).** The hook command is `"$ZUCCHINI_SPAWNER_BIN" prune-reminder-hook` (a self-contained CLI subcommand in `main.rs`, no jq/script-file dependency — Rust parses the PostToolUse payload from stdin); after any tool result whose serialized `tool_response` exceeds `PRUNE_REMINDER_MIN_TOOL_RESPONSE_BYTES` (`prune.rs`) it returns `additionalContext` nudging claude to `prune-context` the output. **It also fires unconditionally for `tool_name == "Skill"`**: a Skill (and slash-command) call injects its real, often multi-100KB payload as a SEPARATE `user`/`isMeta` frame threaded by `sourceToolUseID`, NOT in `tool_response` (which is a tiny "Running skill …" ack), so the size gate alone never catches the biggest prunable chunk a turn accrues. The PostToolUse payload carries no `sourceToolUseID` and the injected body frame triggers no hook of its own, so the Skill tool call is the only handle — and the body is reclaimable via `prune-context --tool-name Skill` (the claude pruner blanks the linked `sourceToolUseID` body, not just the ack; see `adapters/claude.rs::blank_claude_entry`). This reinforces `PRUNE_CONTEXT_INSTRUCTION` at the recency frontier — claude deprioritizes the one-time `--append-system-prompt` standing order (codex/gemini comply from it; claude didn't), so the reminder is re-surfaced right after each heavy result. This is config-injection, which the rule above otherwise forbids — it's sanctioned only because it reinforces *our own* prune feature, not user policy. It stays safe because `--settings` **merges** with (never replaces) the user's `~/.claude/settings.json` / project hooks (verified empirically), so user-configured hooks survive the spawn; the hook never errors or writes partial output (always exits 0). Don't extend this into curating other claude config.

## Hot reload (author's machine)

Two launchd agents in `~/Library/LaunchAgents/`: `chat.zucchini.spawner` (the spawner) and `chat.zucchini.spawner-watcher` (runs `dev-watch.sh` on changes — builds and stages into `~/.zucchini-spawner/dev-update/`, which the running spawner's updater applies once no agent is busy, killing the warm idle residents). Watcher `WatchPaths` covers `src/` **and** `Cargo.toml`, so version bumps rebuild automatically. The machine's `spawner_version` shown in app settings is the *running* binary's `CARGO_PKG_VERSION`, written at startup — it lags until the updater swaps the binary and the spawner respawns.

## Public GitHub mirror

Mirrored to `github.com/zucchini-chat/zucchini-spawner` — the only Zucchini code that runs on user machines, so the only one we open-source. Push-only via `git subtree`; remote `spawner-public` uses SSH alias `github_zucchini_admin`. Plan + supply-chain rationale (cosign-verified releases via Sigstore, dual update channel `users.spawner_source`): `tmp/verifiable-spawner.md`.

**Sync the mirror after committing spawner changes.** From monorepo root:

```
git subtree split --prefix=zucchini-spawner --branch=spawner-export && git push spawner-public spawner-export:main
```

Subtree split reads committed history only, so a dirty working tree is fine. Required before tagging a release once cosign verification ships — the public commit at the tag is what the Sigstore signature binds to; without the sync, the release can't be reproduced or verified.
